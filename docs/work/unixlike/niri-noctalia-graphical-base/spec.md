# Build the shared Niri and Noctalia graphical base

kind: spec
date: 2026-09-23
scope: unixlike
status: approved
review-by: 2026-10-23
issue: #332

Agreed with the maintainer on 2026-09-23 as roadmap order 8. The reference is
Ryan Yin's MIT-licensed `ryan4yin/nix-config` at
`3b13291216bbea04169360b9d8a18a210d816c04`; this work ports selected behaviour
into this repository's concern-first module classes rather than importing its
tree.

## Problem

The repository has graphical terminals and fonts in `homeManager.desktop`, but
no Linux graphical system class, Linux graphical home class, compositor,
desktop shell or automated graphical-session check. The UTM and VMware guests
therefore have only the headless recovery layer, while the roadmap still needs
a reusable graphical base before any installed host adopts it.

The reference configuration supplies a coherent Niri and Noctalia environment,
but its host switches, out-of-store links, private inputs, hardware settings,
secrets and broad application collection do not fit this repository's
architecture. Copying its import tree would also create a second composition
authority.

## Decisions

### Add classes without adopting them into a host

System services contribute to `nixos.graphical`; Linux-only user configuration
contributes to `homeManager.linuxGraphical`; cross-platform graphical programs
remain in `homeManager.desktop`. Roadmap order 8 defines and tests these
classes. Order 10 alone adds them to the UTM and VMware compositions, so this
work cannot activate or alter an installed guest.

Each concern owns its package, generated configuration and payloads. Feature
files name no host and set no other class's policy.
`unixlike/modules/flake/configurations.nix` remains the only host composition
table.

### Use the locked NixOS and Home Manager modules

The locked nixpkgs provides Niri, XWayland Satellite and the NixOS Niri module;
the locked Home Manager provides the Noctalia and Hypridle modules. No flake
input is added or updated. Niri configuration is generated by its concern and
validated with the locked Niri package. Noctalia configuration is generated
and validated by its Home Manager module.

The system class owns Niri, greetd with tuigreet, PipeWire and WirePlumber,
rtkit, portals, polkit, GNOME Keyring, dconf, graphics and removable-media
services. The Linux graphical home class owns Noctalia, Hypridle, XWayland
Satellite, Fcitx5 with Hangul, XDG user directories and MIME defaults, GTK
integration, and the selected Wayland, media and remote-desktop tools. Existing
WezTerm, Ghostty and font modules are reused unchanged.

### Port behaviour, not personal state

The Niri interaction model, Noctalia integration and core desktop tools are
adapted from the reference. Its fixed home paths, wallpaper and avatar, private
inputs, location and weather, hardware and monitor values, networking,
containers, gaming, messaging applications and excluded creative or recording
applications do not enter this work. Age and SOPS remain a later secrets work
item.

### Adopt the low-cost utility set separately from GUI ownership

`nix-index`, tealdeer and zoxide own their Home Manager modules because they
generate configuration or shell integration. The unconfigured first-candidate
utilities join the shared package concern: nix-output-monitor, nix-tree,
procs, duf, dust, trash-cli, hyperfine, jc, sad, mtr, gping, doggo, DNS tools,
rsync and croc. The later candidates remain candidates until a concrete use
case justifies their closure and platform cost.

### Separate automatic proof from installed-host evidence

An x86_64 NixOS VM test composes the actual graphical classes with a disposable
account. It boots the system services and checks the generated user files and
package set without starting a physical display session. Evaluation, native
build and this emulated runtime are order 8 evidence. An installed VMware or
UTM login, rendering, input, audio and activation are order 10 evidence and are
outside this spec.

## Increments

1. Add the spec and report, the two classes, concern modules and evaluation
   fixtures; verify evaluation.
2. Build the x86_64 graphical closure and validated configurations; record
   native build evidence.
3. Add and run the booted VM check, measure its cost, and record native runtime
   evidence. End the report if every automatic criterion is verified.
